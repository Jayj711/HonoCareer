**阶段 2 落地要点**（与接口文档的差异决策，已确认）：

- `resumeId`/`nextCursor` 对外为 **string**（DB 主键仍 BIGINT，序列化 `str(id)`，与画像一致）。
- `ResumeContentPatchDTO` 只更新传入字段；`education/projects` 为对象数组、`skills/certificates/warnings` 为字符串数组（接口文档标注「结构待定」，联调前需具体化）。

**阶段 5 落地要点**（已确认的 6 项决策）：

- 6 个接口：创建/列表/详情/修改/删除/结束，路由前缀 `/api/v1/sessions`，`sessionId` 对外为 string（DB 主键 BIGINT）。
- 创建时绑定并**快照画像**（`profile_snapshot` 存 type/displayName/baseInfo/detail + `profile_snapshot_version`），冻结会话上下文，避免后续画像编辑影响。
- 简历/材料关联：材料走 `session_materials` 关联表；简历补了一列 `sessions.resume_id`（迁移 `be63112a8a09`，`ON DELETE SET NULL`）。
- 幂等：`clientSessionId` 全局唯一，重复创建直接返回原会话（跨用户占用则 40901）。
- `firstPrompt` 阶段 6 才由 Agent 生成，阶段 5 用简单占位开场白；`stage` 初始 `opening`（InterviewStage/DefenseStage 接口文档「待确认」）。
- `finish` 阶段 5 直接 `active → completed`（返回 `status=completed, reportId=null`），报告生成留到阶段 7（届时先置 `generating_report`）。
- 删会话/删材料时先清 `session_materials` 关联行，避免外键约束阻断。
- 创建时校验 mode↔scene 一致性、画像类型与场景匹配（复用 `SCENE_TO_TYPE` 映射）、简历/材料归属。

**阶段 6 落地要点**（含 3 项「待确认」点决策，已拍板）：

- 3 个接口：`POST /api/v1/sessions/{sessionId}/messages`（发消息）、`GET .../messages`（查消息，游标分页）、`GET .../responses/{responseId}/events`（订阅 SSE）。`messages`/`responses`/`response_events` 三张表阶段 0 已建，**阶段 6 无需新迁移**。
- **两段式流式模型**（接口文档定死）：`POST /messages` 只落库 user 消息 + `responses(queued)` + 首条 `queued` 事件后立即返回 `{userMessageId, responseId, status}`；AI 内容由后台 `asyncio` 任务流式生成，逐段写 `response_events`，客户端另开 SSE 订阅。事件带 `eventId`，支持 `Last-Event-ID` 断点续传。
- **后台生成用 `asyncio.create_task`**（无队列基础设施，阶段 6 先单机）：任务持有独立 `AsyncSessionFactory()` session（请求级 session 已关闭），异常兜底写 `error` + `done` 事件并置 `responses.status=failed`。
- **状态机落库**：当前阶段存 `sessions.stage`，历史在 `messages`，提问数从 assistant 的 `question` 消息计数推导，因此 `state_machine.py` 只留纯函数 `decide_turn`，不再持有内存历史，天然支持断点续跑。
- **幂等**：`clientMessageId` 全局唯一，重复发送返回原 `userMessageId`/`responseId`，不重复推进阶段（跨会话占用则 40901）。

**阶段 6 待确认点决策**（接口文档明确标注「待确认」，本项目自行定义）：

1. **阶段枚举**（`InterviewStage` / `DefenseStage`，原接口文档「待确认」）：
   - 面试：`opening → questioning → summary → ended`；答辩：`opening → presentation → questioning → summary → ended`。
   - 提问数上限 `MAX_QUESTIONS = 3`（`state_machine.py`），`questioning` 问满即进 `summary`。
   - 「追问 followup」暂不纳入阶段机（需 LLM 判断回答质量），留作后续增强。
2. **SSE 事件负载结构**（接口文档只给了外层 `{event, data}`，内层 `data` 未定义）：每个 `SSEEventType` 的负载约定如下，`response_events.data` 存负载、`type`/`eventId`/`timestamp` 由行本身推导：
   - `queued`/`thinking`/`done` → `{}`
   - `stage_changed` → `{stage, previousStage}`
   - `message_delta` → `{content}`（文本增量）
   - `message_completed` → `{content, messageId}`（全文 + assistant 消息 id）
   - `error` → `{code, message}`
   - `report_ready` → `{reportId}`（阶段 7 才触发，暂占位）
3. **assistant 消息的 `client_message_id`**：该列 `unique=True, nullable=False`，assistant 消息无客户端幂等键，用占位值 `assistant:{responseId}`（全局唯一）。

**其它约定**：消息列表游标分页按 `id` **正序**（聊天时间序，与 sessions 的倒序不同，因为聊天要按时间从头读）；`limit` 默认 20、1~50；发消息校验 `session.status == active`，非进行中报 40001。语音输入（`inputMode=voice`）阶段 6 只落 `audio_id`，ASR 留阶段 9。`seq` 用 `max(seq)+1` 计算，单用户顺序发送无竞争；并发发消息的 seq 竞态留待后续加唯一约束。

**阶段 7 落地要点**（评分报告 + 弱项，4 个接口）：

- 4 个接口：`GET /api/v1/sessions/{sessionId}/report`、`POST /api/v1/sessions/{sessionId}/weak-points`、`GET /api/v1/weak-points`、`DELETE /api/v1/weak-points/{weakPointId}`。`reports`/`weak_points` 两张表阶段 0 已建，**阶段 7 无需迁移**。
- **报告异步生成**：`finish` → 建 `Reports(status=pending)` + 会话置 `generating_report` + `report_status=pending` → 后台任务 `run_report`（DeepSeek 结构化评分卡，正则兜底）→ 落报告 + 回写 `sessions.overall_score` + 置 `completed` / `report_status=ready`。复用阶段 6 的 `asyncio.create_task` 后台任务模式。
- **就绪信号轮询**：客户端轮询 `GET /report`（`status: pending → ready / failed`），不推 SSE；`report_ready` 事件类型保留占位。
- **弱项独立于报告**：手动 `POST /weak-points` 才建 `WeakPoints` 行；报告自动产出的 `weak_point_tags` 不建行，两者仅共用同一套 `dimensionKey` 枚举。

**阶段 7 待确认点决策**（接口文档「待确认」/ 建议拍板项，已确认）：

1. **评分维度封闭枚举**（`dimension_key → label`，报告维度与弱项 `dimensionKey` 共用一套）：
   - 面试：`communication` 沟通表达 / `professional` 专业能力 / `logic` 逻辑思维 / `fit` 岗位匹配 / `learning` 学习能力；
   - 答辩：`topic_value` 选题价值 / `research_depth` 研究深度 / `expression` 答辩表达 / `adaptability` 临场应变；
   - 各维度 `score` 0–100，`overallScore` 由 LLM 直接给出（不做加权公式，留待联调）。
2. **报告生成时机**：`finish` 触发异步生成；状态机走到 `ended` 不自动生成（必须显式 `finish`）。
3. **弱项与报告解耦**：报告的 `weakPointTags` 只落字符串数组，不自动建 `WeakPoints` 行。
4. **`report_ready` 通道**：以轮询 `GET /report` 为准；SSE `report_ready` 事件类型保留但不推送（现有 SSE 是 `responseId` 粒度、报告是会话粒度，接口文档未定义会话级事件流）。
5. **`WeakPointVO` 补 `sessionId`**（接口文档自述「缺 sessionId 无法定位会话」），DB 已有 `weak_points.session_id` 列。
6. **`GET /weak-points` 不分页**：按接口文档返回普通数组（`data` 为 `array`），仅此端点例外，其余列表仍走 `PageResult`；用可选 `mode` 过滤。

**阶段 8 落地要点**（长期记忆，4 个接口）：

- 4 个接口：`GET /api/v1/users/me/memory-settings`、`PATCH /api/v1/users/me/memory-settings`、`GET /api/v1/users/me/memories`、`DELETE /api/v1/users/me/memories`。`memory_settings` / `memories` 两张表阶段 0 已建，**阶段 8 无需迁移**。
- **记忆写入挂到阶段 7 的 `run_report` 尾部**（同一后台任务、同一 db session，不再开第二个任务）：`services/memory.py::sync_memories_from_session` 读 `memory_settings.enabled`，关则跳过；开则 DeepSeek（`temperature=0`）从 transcript 提炼 1~3 条 `Memories` 行。提炼失败 catch + log，**不影响报告主流程**。
- **设置惰性 upsert**：`GET` 无行时返回默认 `{enabled:false, retentionPolicy:"permanent"}` 且**不落库**；`PATCH` 走 upsert（有则改、无则建）。
- `GET /memories` **不分页**（同 `GET /weak-points`），返回普通数组，按 `id` 倒序。

**阶段 8 待确认点决策**（接口文档「待确认」/ 建议拍板项，已确认）：

1. **`retentionPolicy` 语义**：定义 str-Enum `RetentionPolicy`，现阶段唯一取值 `permanent`（永久保留，默认）；`retention_policy` 列默认 `permanent`；`GET` 恒返回、`PATCH` 不接收该字段（接口文档 `PATCH` 只收 `enabled`）。真正的「按时间/条数自动清理」机制留待产品定义后再加（届时补 `days`/`max_count` 等取值与后台清理任务）。
2. **`MemoryItemVO` 字段收敛**（旧版 `summary` vs v2.0 `content`）：用 `content`（DB `memories.content` 列已存在）；`source` **保留** → 映射 `source_session_id`；`createdAt` **保留** → 映射 `create_time`。
3. **`source` 取值**：直接存/返 `str(session_id)`（来源会话 id 字符串）。
4. **记忆写入时机**：挂 `run_report` 尾部同步（同一后台任务、同一 db session），提炼 1~3 条；`enabled=false` 时跳过。
5. **`GET /memories` 分页**：不分页，返回普通数组按 `id` 倒序。
6. **`memory_settings` 惰性语义**：`GET` 无行返回默认不落库；`PATCH` upsert。
7. **`DELETE` 边界**：只删 `memories` 表当前用户全部行，**不动 `memory_settings`**（开关不是记忆本体）。

**阶段 9 落地要点**（语音，2 个接口）：

- 2 个接口：`POST /api/v1/speech/asr`（`multipart/form-data`：`audio` 文件必填、`sessionId`/`language` 可选 → `AsrVO{audioId, text, confidence, durationMs}`）、`POST /api/v1/speech/tts`（`application/json`：`TtsDTO{text 必填, voiceId, speed}` → `TtsVO{audioUrl, audioId, durationMs, expiresAt}`）。`audios` 表阶段 0 已建，**阶段 9 无需迁移**。
- **供应商抽象**：`app/speech/base.py` 定义 `SpeechClient`（`asr` / `tts`）+ `app/speech/aliyun.py` 适配阿里云智能语音交互（NLS）。密钥进 `.env`（`ALIYUN_AK_ID` / `ALIYUN_AK_SECRET` / `ALIYUN_NLS_APPKEY`），`.env.example` 只放占位符。
- **音频存储**：本地 `uploads/speech/{uuid}.{ext}` + 下载路由 `GET /api/v1/speech/audio/{audioId}`；后续改阿里云 OSS（届时 `audioUrl` 用预签名 URL、`expiresAt` 才有意义）。
- **消息链路衔接**：`MessageSendDTO.inputMode=voice + audioId` 已就位；`services/message.py` 落库时若 `inputMode=voice` 且带 `audioId`，从 `Audios` 回填 `asr_confidence`（现硬编码 `None`）。

**阶段 9 待确认点决策**（已确认）：

1. **实现路线**：路线 A —— 后端实现 `/speech/asr` + `/speech/tts`，接第三方供应商；端侧可直连供应商或走后端（二选一）。
2. **供应商**：阿里云智能语音交互（NLS）；`SpeechClient` 抽象 + `AliyunSpeechClient` 适配器，密钥进 `.env`。

## 可升级点

> 记录 Agent 层当前「手搓实现」与业界框架（LangChain / LangGraph）的对应关系，以及将来升级的触发条件与迁移路径。当前 `requirements.txt` **刻意不引入** langchain / langgraph，属手搓。

**现状 → LangChain / LangGraph 对应**：

| 本项目 | LangChain / LangGraph |
|---|---|
| `app/llm/base.py` 的 `LLMClient`（`chat` / `stream_chat`） | `BaseChatModel` 抽象 |
| `app/llm/deepseek.py` 的 `DeepSeekClient`（OpenAI 兼容 `/chat/completions`） | `ChatDeepSeek` / `ChatOpenAI(base_url=...)` |
| `app/agent/prompts.py` 的 `build_system_prompt` | `ChatPromptTemplate` |
| `app/agent/state_machine.py` 的 `decide_turn`（纯函数） | LangGraph 的 conditional edge / router 函数 |
| `app/agent/orchestrator.py` 的 `run_response` | LangGraph 的 `StateGraph`（nodes + edges） |
| `messages` + `sessions.stage` 落库、提问数从历史推导 | LangGraph 的 Checkpointer（状态持久化） |
| `response_events` 表 + SSE 逐事件推送 | LangGraph 的 `astream_events` / streaming modes |

**触发条件**（出现以下任一，再评估引入 LangGraph）：

- 阶段 7 / 8 引入**多步工具调用**（查题库 / 查 JD / 查材料 / 打分），编排分支明显复杂化；
- 需要 **human-in-the-loop 中断 / 恢复**（如「追问回答质量」需人工确认）；
- 需要**跨进程、崩溃可重放的持久队列**（当前 `asyncio.create_task` 单机、进程重启即丢，见阶段 6 落地要点）。

**迁移路径**（因边界已切干净，迁移成本低）：

- `decide_turn` → LangGraph conditional edge（路由函数）；
- `_load_context` / `_load_history` / `_count_questions` → 图节点；
- 自建 `sessions.stage` + `messages` → LangGraph `Checkpointer`（`AsyncPostgresSaver` 等）替换；
- `_llm.stream_chat` → 保持 `LLMClient` 抽象不变，或换 `ChatDeepSeek` 适配。

**为什么不现在引入**：状态机仅 5 阶段 / 3 问上限，纯函数 80 行更透明；异步硬约束 + 自建 `AsyncSessionFactory` 与框架 saver 强绑定反而别扭；薄分层 + 统一响应与框架的对象式编排不完全对齐。

## 语音边界

后端负责文本 Agent（文本对话与流式输出）。ASR / TTS 由后端提供**可选**接口（阶段 9 落地 `POST /speech/asr` + `POST /speech/tts`，接第三方语音供应商）；端侧可直连供应商省带宽，也可走后端（统一密钥管理与 `Audios` 落库）。见「阶段 9 落地要点」。

## 开发规范

**分层**：`api`（路由，薄）→ `services`（业务）→ `schemas`（DTO/VO）。路由只做参数绑定 + `Result.success(...)` 包裹，业务逻辑与 `BizError` 抛错都在 service 层。

**统一响应**：所有非 SSE 接口返回 `{ code, message, data, requestId }`，`code=0` 成功；业务错误 HTTP 状态码恒 200，用 body 里的 `code` 区分。FastAPI 默认的 422 参数校验错误已统一拦截，转成 `40001`（HTTP 200），`message` 带上出错字段路径（如 `参数错误: body.account`）。

| code | 含义 |
|---|---|
| 0 | 成功 |
| 40001 | 参数错误 |
| 40101 | 未登录 / token 缺失 |
| 40102 | token 过期或无效 |
| 40301 | 无权限 |
| 40401 | 资源不存在 |
| 40901 | 冲突（账号已存在 / 画像版本冲突） |
| 50001 | 服务器内部错误 |

**鉴权**：请求头 `Authorization: Bearer {accessToken}`；access token 用 JWT（HS256，`sub`/`iat`/`exp`），refresh token 为不透明随机串、存库并轮换（刷新时吊销旧 token），登出吊销该用户全部 refresh token。

**分页**：列表统一游标分页 `PageResult = { items, nextCursor, hasMore }`，游标为上一页最后一条的 id。

**其它**：日志对 `api_key`/`secret`/`token`/`password`/`Authorization` 等敏感字段自动脱敏（见 `config.py`）。
